# Standard-operation generator

Run from the repository root. This tooling lives outside the Maven backend on purpose: `backend/` holds only the
Maven modules; the generator writes into it and its own scratch files stay in `tools/backend/crud/target/`.

Produces the code of every resource whose contract maps column for column onto its table (JAVA-CODING-RULES §4,
"Generated standard operations"): per resource an entity, repository, mapper and service, per contract interface a
controller (unserved operations answer 501), and per module the contract test spec (`crud-spec.json`), the
`<Module>CrudComponentTest` that runs it and the `<Module>ControllerStubsTest`. Generated files start with
`// GENERATED by tools/backend/crud`; the generator never overwrites a hand-written file (it writes its version to
`target/conflicts/` instead — `merge_controllers.py` merges the controllers that mix both: people's `PersonController` and iam's
`UserAccountController`). A hand-written `<Resource>Rules` component next to a generated service is called at fixed
points (`beforeWrite`, `beforeUpdate`, `beforeDelete`, `afterDelete`) for the resource's own invariants.

Secrets are generated too: a `writeOnly` contract field over a `<name>_enc` column is encrypted with core's
`FieldCipher` before it is stored, never returned, never filterable, and shown through its `<name>Masked` field; the
contract test proves the stored value is an envelope and never the plaintext.

State transitions listed in `transitions.json` are generated too: a POST on one row (`…/{id}:publish`) that is allowed
only from the listed states (else 409 `INVALID_STATE_TRANSITION`), checks the body `etag` when the request carries one
(412) and the `If-Match` header when the operation declares it (428 without, 412 when stale), sets only the listed columns in one guarded `UPDATE … WHERE row_version = :expected`, and writes an audit record
(with the request's reason) and a `<resource>.<step>` outbox event in the same transaction. A transition is listed only
when it changes nothing but those columns; the generator stops with an error when an entry does not match the contract
or the schema, or when its resource is not generated. `api/state-machines.md` is written from the same file.

```bash
(cd backend && mvn -pl contracts -am install -DskipTests)   # the generated contract sources the generator reads
PGHOST=localhost PGUSER=postgres tools/backend/crud/catalog.sh   # scratch database with every migration + target/catalog.json
python3 tools/backend/crud/gen.py                  # main code + tests; prints what it skipped and why (target/report.json)
python3 tools/backend/crud/merge_controllers.py
python3 tools/backend/operation_status.py          # api/operations-status.md: every operation, served or 501, and why
PGHOST=localhost PGUSER=postgres python3 tools/backend/crud/specgen.py  # samples and transition steps, proven against the scratch database
python3 tools/backend/conformance.py               # the design rules the compiler and the gates cannot check (0 violations)
```

| File | Role |
|---|---|
| `model.py` | Joins the OpenAPI standard operations with the catalog; decides which resources map cleanly |
| `gen.py` | Analysis (scope, uniqueness, references, children) and the Java writers |
| `javasrc.py` | Reads the exact method signatures and model fields from the generated contract sources |
| `fmt.py` | Unused imports, 120-column wrapping (the gates are the same as for hand-written code) |
| `merge_controllers.py` | Puts the hand-written operations back into the controllers that also serve generated ones |
| `transitions.json` | The generated state transitions: guard (column → allowed values), the columns set, whether a reason is kept |
| `specgen.py`, `overrides.json` | Sample create/update payloads and the minimal parent rows; `overrides.json` holds the few samples that multi-column CHECK constraints need |
| `tenant_sql.py` | Adds `tenant_id = :tenantId` to every statement over a tenant table (each FROM table and JOIN … ON); `apply_tenant_sql.py` applies it once to hand-written repositories |
| `gen_events.py` | Each module's reference cleanup (database/logical-references.md, both the forward and the against-DAG table; an unknown action text stops it): the `<Module>ReferenceCleanup` subscriptions, their tenant-filtered statements and a component test per module (`reference-cleanup.json`, written by `specgen.py`) |
| `gen_operations.py` | The long-running operation endpoints (`List`/`Get`/`CancelOperation`) of every module with an `operation` table |
| `introspect.sql`, `catalog.sh` | The schema catalog the generator reads |

Requirements: Python 3.11+ with PyYAML, `psql`, PostgreSQL 16.
