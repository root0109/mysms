# MySMS database design

The complete relational design for MySMS: one PostgreSQL database model that covers school administration (K-12), higher-education academics, online learning (LMS), finance, HR/payroll, library, transport, communication and careers.

## Conventions

- **Database:** PostgreSQL 16+. One schema per module; `snake_case` names; table names are singular.
- **Lightweight by design:** plain tables, constraints, indexes and row-level-security policies only. No extensions, stored functions, procedures or triggers; all behaviour (workflows, derived values, notifications, audit stamping, partition maintenance) lives in the application. Case-insensitive uniqueness (login name, e-mail) uses `lower(column)` expression indexes, so the application compares with `lower()` too.
- **Primary key:** every table has `id uuid` (UUIDv7 generated by the application for index locality; `gen_random_uuid()` is the database fallback). Exceptions: partitioned tables use `(id, <partition column>)`; the per-module `outbox_event` uses an identity bigint because publish order matters.
- **Enumerations:** stored as `varchar` with a `CHECK (col IN (...))` constraint; the allowed values are listed in the data dictionary. Change a list with `DROP CONSTRAINT` / `ADD CONSTRAINT ... NOT VALID; VALIDATE CONSTRAINT` so large tables are not locked.
- **Money:** `numeric(14,2)` with a `currency_id` (logical reference to `master.currency`) on the row or its parent.
- **Files:** binary content is never stored in tables. Single-file fields are `*_file_id` (logical reference to `platform.file_object`, obtained through the platform API); multi-file fields use `platform.entity_attachment`. Files have a lifecycle (`pending / available / quarantined / deleted`) and a unique `(storage_disk, storage_key)`.
- **Audit & concurrency:** every business table has `created_at`, `created_by`, `updated_at`, `updated_by`, `deleted_at` (soft delete) and `row_version` (optimistic locking; the API's ETag). `created_by` / `updated_by` hold the `iam.user_account.id` of the actor and are deliberately not FK-constrained so audit history survives account deletion. Append-only tables (`platform.audit_log`, `assessment.result_change_log`, outbox/inbox, gateway events) carry only what an immutable record needs. A module never writes `platform.audit_log` directly: its audit records go into its own `outbox_event` in the same transaction as the change, and the platform module materialises them into `platform.audit_log`.
- **Uniqueness vs soft delete:** every business unique key is a partial unique index `WHERE deleted_at IS NULL`, so a soft-deleted row never blocks re-creation. Absolute (non-partial) uniqueness is deliberate in three places: money-integrity dedupe keys (gateway transaction / receipt / refund references — a soft-deleted payment must still block a replayed webhook), physical keys and login identifiers (storage key, host name, token hash, document numbers), and the `(id, tenant_id)` composite-FK targets below. Sort-order and versioning-chain uniques on pure composition rows are plain `UNIQUE ... DEFERRABLE INITIALLY IMMEDIATE` constraints instead, so reordering and version-supersede flows can update both rows in one transaction.
- **Document numbers** come from the issuing module's own `number_sequence` table, read with `SELECT ... FOR UPDATE` inside the issuing transaction: `admission` (application numbers), `finance` (invoice and receipt numbers), `hr` (employee codes), `library` (card, accession and purchase-request numbers), `lms` (certificate numbers), `payroll` (payslip numbers), `sis` (enrolment admission, identity-card, bonafide-certificate and registration reference numbers). No module issues numbers from another module's table. Posted invoices, paid payslips, issued certificates and published marksheets are never updated; corrections are new documents (credit note, replacement payslip, result change via the logged workflow).
- **Deletes:** default `ON DELETE RESTRICT`; `CASCADE` only into pure composition rows of parents that are never hard-deleted (lines, links, child records); `SET NULL` for optional references. Identity rows never cascade into grading, consent, money or audit evidence. Every foreign-key column and every logical-reference column has an index. The API returns 409 when a delete is blocked by an in-module reference; rows referenced from other modules are never hard-deleted — they are archived (status) and the owner publishes the event its dependents act on.
- **Versioned authoring content (LMS):** lesson, quiz, question, assignment and rubric are shared, versioned artefacts (`version`, `superseded_by_id`, `published_at`): a published version is immutable, editing creates a new version. Chapters, content items, grading categories and release rules are copied per cohort (`copied_from_id`); graded evidence snapshots what it was graded against (`rubric_version`, `points_awarded`, `points_possible`, `max_marks`).
- **Secrets:** columns ending `_enc` hold application-encrypted values in the envelope `v1.<key_id>.<iv>.<ciphertext>` (key per tenant, rotatable by `key_id`): gateway and webhook secrets, bank account numbers, national ids, meeting start/join links, conferencing OAuth tokens, MFA secrets and channel/tool secrets. They are write-only through the API; display uses `*_masked` columns. Passwords and tokens are stored only as hashes.
- **Partitioned high-volume tables:** `platform.audit_log` (`occurred_at`), `attendance.attendance_record` and `attendance.staff_attendance` (`attendance_date`), `comms.outbound_message` and `comms.in_app_notification` (`created_at`), `lms.access_log` (`accessed_at`), `lms.content_view_session` (`started_at`) are range-partitioned by month. The baselines create monthly partitions for 2026–2027 plus a `DEFAULT` partition that must stay empty; the application's maintenance job (core's `PartitionMaintenanceJob`: at startup and then daily, plain DDL through JDBC) creates the current month and `mysms.partitions.months-ahead` months ahead (default 3), logs an ERROR when a default partition has ever been written (a month was missing; its own month can then not be attached until those rows are moved), and — only when `mysms.partitions.retention-months` is set — detaches and drops months that ended before the retention window (default 0: nothing is dropped). `attendance_record.attendance_date` copies the sheet date and is kept in step by a composite FK with `ON UPDATE CASCADE`. No foreign key points at a partitioned table, and partitioned-table list queries must always carry a time-range filter. On partitioned tables the primary key is `(id, <partition column>)`, so the database enforces id uniqueness only within one partition-key value; global id uniqueness is guaranteed by the application generating UUIDv7 ids (collision odds are negligible), and `Get`-by-id reads remain correct because the API resolves these rows with the id plus the time range the client supplies.
- **Reference data (pick-lists):** one shape — `code` (stable key), `name`, `sort_order`, `is_active`, unique `(scope, code)` ignoring soft-deleted rows. One scope rule — global read-only catalogues are only `master.*` geography/currency plus `iam.permission`, `iam.setting_definition` and `comms.notification_type` (the two iam catalogues are product data seeded by migrations: `V1_030_003` the settings, `V1_030_004` every permission code of the contracts, generated by `tools/gen_permission_catalogue.py`); everything a school can edit is tenant- or institution-owned, with platform defaults **copied into each tenant at provisioning** (no shared `NULL`-tenant rows anywhere).
- **Personal-data consent:** `people.consent_record` holds who consented to what (for minors, a guardian flagged `is_legal_guardian`), under which policy version, and when it was withdrawn; the API refuses consent-gated operations without it. Consent evidence is never cascaded away.
- **Student leave / staff attendance:** approved `sis.student_leave_request` rows explain absences (`attendance_record.leave_request_id`); staff presence is `attendance.staff_attendance` with `hr.leave_application` / `hr.leave_balance` behind it.

## Multi-tenancy and security model

- Every tenant-owned table (446 of them) has `tenant_id uuid NOT NULL` (one exception: `master.outbox_event.tenant_id` is nullable, because global master data publishes events with no tenant; its policy is `tenant_id IS NULL OR tenant_id = current_setting('app.tenant_id', true)::uuid`) — logically `platform.tenant.id`, with no foreign key: tenant validity comes from the authenticated token and host→tenant resolution, and RLS scopes every row. Global tables (no `tenant_id`): `master.country`, `master.state_province`, `master.city`, `master.currency`, `platform.tenant`, `platform.saas_plan`, `platform.reserved_keyword`, `platform.sales_enquiry`, `platform.system_setting`, `iam.permission`, `iam.setting_definition`, `comms.notification_type`, `comms.notification_type_property`; and `iam.tenant_directory`, keyed by tenant but read at sign-in before a tenant is known, so it has no row-level security (it holds tenant codes and status only).
- **Tenant-composite foreign keys (inside a module).** Wherever both sides of a relationship are tenant-owned, the FK is `(column, tenant_id) REFERENCES parent (id, tenant_id)` against the parent's `UNIQUE (id, tenant_id)`. A reference can therefore never point into another tenant, even if application code passes the wrong id. `ON DELETE SET NULL` FKs null only the business column (PostgreSQL 15+ column list), never `tenant_id`. For a cross-module logical reference the same guarantee comes from the tenant-scoped API lookup at write time, with RLS on both sides as the backstop.
- **Row-level security.** Every tenant-owned table (446 of them) has `ENABLE` + `FORCE ROW LEVEL SECURITY` and the policy `tenant_isolation USING (tenant_id = current_setting('app.tenant_id', true)::uuid)`. The application sets `SET LOCAL app.tenant_id = '<uuid>'` at the start of every transaction (one line in the Spring JDBC transaction decorator).
- **Roles.** Four database roles, created by operations (not by the migrations): `mysms_migrate` owns the schemas and runs Flyway; `mysms_app` is the application login — not the table owner, so `FORCE` RLS applies to it — with DML granted on module schemas; `mysms_relay` has `BYPASSRLS` and is the role of each module's **outbox relay** (the background publisher that drains that module's `outbox_event` table across all tenants) — the only `mysms_app`-side process that legitimately reads across tenants. Flyway grants it `USAGE` on the module's schema, `SELECT, DELETE` on its `outbox_event` and `inbox_event` and `UPDATE` of `outbox_event.published_at` and `.publish_error` only (core's `ApplicationRoleGrants`): no business table, and it can never write an event. The relay uses a pool of its own for those statements alone (`relay-username`, `MYSMS_DB_RELAY_USER`), and a service refuses a relay user that is its application or migration user. `mysms_platform_admin` has `BYPASSRLS` for platform console and support tooling, used only by the platform service. The partition-maintenance job connects as the schema owner (`mysms_migrate`, the service's `migrate-username`), because PostgreSQL lets only a table's owner attach or detach its partitions; it runs DDL and catalog queries only and reads no rows. CI runs `verification/smoke.sql`, which proves isolation with a non-owner role.
- `platform.tenant_domain` maps every host (subdomain or custom domain) to its tenant; requests and deep links resolve the tenant from the host.

## Module boundaries

Each module is a bounded context and a separately deployable service, and **its schema may live on its own PostgreSQL instance**. The schema is identical whether all 21 modules share one instance or each has its own — there is no deployment-specific migration:

- **No cross-module (cross-schema) foreign keys — none.** All 468 foreign keys are inside one schema and always enforced. A reference into another module is a plain, indexed uuid column — a *logical reference* — protected by five mechanisms: (1) the business service validates the id through the owning module's tenant-scoped API before writing it; (2) referenced entities are never hard-deleted, only archived — every money- and evidence-protecting `RESTRICT` rule is an in-module FK and stays in the DDL; (3) the owner's deleted/archived events drive cleanup in dependents; (4) a periodic per-module reconciliation job verifies reference ids against the owner and reports orphans; (5) RLS is the cross-tenant backstop. The register of all 494 references, with each dependent's event action, is `logical-references.md`.
- **No cross-schema writes.** A module reads and writes only its own schema. Every service schema therefore has its own infrastructure tables: `outbox_event` and `inbox_event` (all 21), `idempotency_key` and `operation` (all except `master`, whose global reference data is written only by platform operations), and `number_sequence` where the module issues numbers (7 modules, see *Conventions*). Audit records reach `platform.audit_log` through the module's own outbox.
- **No cross-schema reads either.** Data owned by another module is fetched through that module's API (ids plus compact "card" projections), never joined in SQL — a join across schemas would break the moment the schemas are on different instances.
- **Global tables** (no `tenant_id`; written by platform staff, read by everyone the contract allows): their changes run in a transaction that binds no tenant (with no tenant in the call context either, even when a signed-in tenant user submits a public form) and publish events and audit records with no tenant. In `platform.outbox_event`, `comms.outbox_event` and `platform.audit_log` (like `master.outbox_event`) `tenant_id` is therefore nullable, under three row-level security policies: `tenant_isolation` shows and lets write a tenant's rows to that tenant only; `global_insert` lets a row without a tenant be inserted only by a transaction that binds no tenant; and `global_read` shows such rows only to such a transaction (needed because the inserts read their row back, and the audit insert is `ON CONFLICT DO NOTHING`). So no tenant session can forge a global event or audit record, and no tenant session ever sees one (the relay and support tooling read them as `BYPASSRLS` roles). All three compare with `NULLIF(current_setting('app.tenant_id', true), '')`, because a pooled connection that bound a tenant in an earlier transaction reads the setting back as an empty string. iam keeps `iam.tenant_directory` in step with `platform.tenant`'s events; `source_version` holds the tenant row version last applied, so a late or repeated event never restores an older status. Retiring a global row is a soft delete and is not blocked by tenants' rows that reference it (a tenantless transaction cannot see them): those keep their reference, as with any logical reference.
- **Events:** `outbox_event` is written in the same transaction as the change, published by the module's relay and pruned after publish (a row the relay cannot turn into the module's own event is set aside with its reason in `publish_error`); `inbox_event` stores consumed event ids per tenant (primary key `(tenant_id, event_id)`) so redeliveries are processed exactly once, and the relay prunes processed rows after the inbox retention (30 days by default). Cross-module writes never share a transaction: the caller writes its own rows plus an outbox event; the other module reacts to the event.
- The module dependency graph is a **DAG** (see `erd/00_overview` and ARCHITECTURE.md). 26 references point against the arrow; the owner is unaware of them and their cleanup is driven purely by its events (listed at the end of `logical-references.md`).

## How the core model fits together

**Identity.** A human is one `people.person`. The same person can be a `sis.student` (per institution), a `sis.guardian`, an `hr.staff` member, an `admission.application` applicant and an LMS student. Login is a separate `iam.user_account` linked to the person (`user_type` on the account is only a routing hint). Authority comes only from `iam.user_role` grants — every role belongs to one tenant (platform role templates are copied at provisioning) — optionally scoped to an institution, department, class section, course or LMS course/cohort. A `sis.student_guardian` link by itself grants no data access.

**Academic structure.** `org.institution` → `org.academic_year` → `org.academic_term` (terms nest: quarters inside semesters).
- *K-12 schools:* `academics.grade_level` + `academics.section` combine per year into `academics.class_section`. Subjects are offered to a class through `academics.class_subject`, taught by staff through `academics.teaching_assignment`, planned with `academics.curriculum_unit` and `academics.lesson_plan`.
- *Higher education / coaching:* `academics.program_level` → `academics.program` → `academics.course` with a term/credit-aware subject plan (`academics.course_subject`: term number, credits, category, max marks) → `academics.batch`.

**Placement vs registration vs learning access.** These are deliberately separate records:
- `sis.student_enrollment` places a student in a class section for one academic year (K-12) — as dated history: `effective_from` / `effective_to`, `previous_enrollment_id` and `change_reason` record every section change, transfer and re-admission; one *open* row per student and year.
- `sis.program_enrollment` registers a student on a course and batch (higher education); `sis.subject_registration` (bound to year, term and program enrollment) holds subject choices, each line pointing at the course-plan row it registers.
- `lms.enrollment`, `lms.cohort_enrollment` and `lms.learning_program_member` give access to online learning and do not imply school placement.

**Online learning: self-paced courses and teacher-led cohorts.** `lms.course` is a versioned course template. Its outline is `lms.chapter` holding `lms.lesson` pages and `lms.content_item` placements (a placement puts one thing in a chapter — lesson, file, assignment, quiz, discussion prompt, participation activity, web resource, e-book, external tool, live class, link or programming exercise — with visibility/attempt windows, points, weight, grading category and rubric; cohort-wide items carry `cohort_id` with no chapter). A `lms.cohort` runs a course for real students (and can link back to the school structure: class subject, batch, academic year): the outline is copied into cohort-owned chapters and items (`copied_from_id` back to the template), so teachers adapt a cohort without touching the template.

**Grades.** Per-attempt data stays with the activity (`lms.quiz_submission` with its attempt number and unique per attempt, `lms.quiz_answer`, `lms.assignment_submission`, posts). The official grade for a graded item is one `lms.gradebook_entry` (with `points_possible` snapshot), every change in `lms.grade_change_log`; rubrics are applied through `lms.rubric_assessment` (rubric version + points snapshot); extensions through `lms.item_override`; conditional release through `lms.release_rule` → conditions/targets → `lms.release_grant`.

**Official assessment.** Exams live in `assessment`: `exam_session` → `exam` → one `exam_result` row per student and paper (seating, attendance, marks, grade, credits), changed only through the marks-entry workflow which writes `assessment.result_change_log`. Marksheets aggregate results per student (with credits/SGPA/CGPA for higher education) and are published explicitly (`published_at`, `visible_to_guardians`). LMS scores are not official results.

**Presence.** School attendance is `attendance.attendance_register` → `attendance_sheet` → `attendance_record` (per student, partitioned by date). Approved student leave explains absences. Staff presence is `attendance.staff_attendance`. Live-class participation and video watch time are engagement data, not attendance.

**Money.** Fee structures bind a fee plan to a year and a class/program; publishing generates `finance.student_fee_due` rows (concessions applied, duplicates impossible). Invoices are documents (draft → posted; credit notes correct them). `finance.payment` records money received (gateway or counter: cash/cheque/DD/transfer) with `payment_allocation` splitting it across invoices and dues, `finance.refund` reversing it, and `finance.gateway_event` keeping the webhook trail; a gateway payment can never be recorded twice. `payment.invoice_id` is only the checkout convenience pointer (the invoice the payer was looking at); the **allocation rows are the accounting truth** — reporting and balance maths always read `payment_allocation`, never `payment.invoice_id`, and a payment may legitimately be allocated across several invoices or dues regardless of that pointer. Allocations carry the same currency as their payment and target by construction (composite FKs to `(id, currency_id)`). SaaS subscriptions (`platform.tenant_subscription`) and staff pay (`payroll.*`) are separate flows.

## Polymorphic references (by design, no foreign key)

A few columns point to rows in different tables depending on a companion type column. They are validated by the application:

| Column | Meaning |
|---|---|
| `platform.file_object.owner_entity_type` / `owner_entity_id` | Polymorphic owner when the file belongs to one record. |
| `platform.entity_attachment.entity_type` / `entity_id` | Polymorphic owner, e.g. assessment.homework_submission. |
| `platform.tag_assignment.entity_type` / `entity_id` | Polymorphic target. |
| `platform.entity_note.entity_type` / `entity_id` | Polymorphic target. |
| `platform.audit_log.subject_type` / `subject_id`, `causer_type` / `causer_id` | Polymorphic subject and actor. |
| `iam.user_role.scope_id` | Polymorphic scope record id (NULL when scope_type = tenant). |
| `comms.outbound_message.related_entity_type` / `related_entity_id` | Record the message is about. |
| `comms.in_app_notification.entity_type` / `entity_id` | Record the notification is about (deep-link target). |
| `comms.content_view.content_id` | Item viewed (table given by content_type). |
| `platform.deletion_log.entity_id` | Deleted row id. |
| `comms.calendar_export.entity_id` | Exported item id. |
| `lms.forum_topic.linked_entity_id` | Record the topic discusses. |

Everywhere else a reference to another row is either a declared foreign key (same module) or a registered logical reference (another module, see `logical-references.md`). In-module references that can target one of several tables use one typed nullable FK per target plus a `CHECK (num_nonnulls(...) = 1)` constraint (e.g. `lms.lesson_activity`, `lms.content_item`, `lms.timetable_entry`, `finance.payment_allocation`, `comms.task_assignee`, `comms.reaction`).

## Applying the schema (Flyway / Spring Boot)

Migrations follow Flyway naming: `V<release>_<module order>_<sequence>__<description>.sql`. Version `1.010.001` is the baseline of `master`, `1.150.001` the baseline of `lms`. Flyway refuses a version lower than the highest one already applied (`out-of-order` stays off), so every later change uses a release number above the baseline: release 2 changes go in the owning module's folder as `V2_<module order>_<seq>__…` (for example `lms/V2_150_001__add_xyz.sql`). There is no cross-module migration folder: a migration only ever touches its own module's schema.

**Post-go-live migration rules** (the baselines are editable only until first production deploy; after that):

1. Additive first: new columns are nullable or defaulted; `NOT NULL` is added after backfill with `ADD CONSTRAINT ... NOT VALID` + `VALIDATE`.
2. No rewrites of big tables in one lock: new enum values via `DROP`/`ADD ... NOT VALID; VALIDATE`; new indexes `CREATE INDEX CONCURRENTLY` in `R__`-style out-of-transaction scripts or maintenance windows.
3. Renames and drops are two releases apart: release N adds the new column and dual-writes in the application; release N+1 drops the old one.
4. Seed/reference data lives in repeatable `R__<module>_reference_data.sql` scripts used as templates by the tenant-provisioning job, not in versioned migrations.
5. Every release is rehearsed by CI: apply all migrations to a clean database, then to a copy with the previous release's schema plus sample data; run `verification/smoke.sql`.

**All modules on one instance (development, small deployments).** Point one Flyway run at every folder:

```yaml
spring:
  flyway:
    locations: classpath:db/migration/master,classpath:db/migration/platform,classpath:db/migration/iam,classpath:db/migration/org,classpath:db/migration/people,classpath:db/migration/academics,classpath:db/migration/sis,classpath:db/migration/hr,classpath:db/migration/payroll,classpath:db/migration/admission,classpath:db/migration/attendance,classpath:db/migration/facility,classpath:db/migration/timetable,classpath:db/migration/assessment,classpath:db/migration/lms,classpath:db/migration/finance,classpath:db/migration/library,classpath:db/migration/transport,classpath:db/migration/comms,classpath:db/migration/frontoffice,classpath:db/migration/careers
    default-schema: public          # flyway_schema_history lives in public
    baseline-on-migrate: false
```

In the Java build each module carries its own folder (`<module>/src/main/resources/db/migration/<module>/`) and runs Flyway against its own DataSource; the assembled application simply runs them all. Flyway runs as `mysms_migrate` (the schema owner); the application connects as `mysms_app`. Data access is plain Spring JDBC (`JdbcClient` / `NamedParameterJdbcTemplate`) with schema-qualified SQL (`lms.course`, `sis.student`); there is no ORM layer, so Flyway is the only thing that creates or changes the schema. The module's transaction executor issues `SET LOCAL app.tenant_id` before any statement.

**Module as its own service (own instance).** The service applies its own folder only and keeps its own `flyway_schema_history` (set `default-schema` to the module's schema). Because no migration and no constraint crosses schemas, the folder applies unchanged on a shared instance or a dedicated one — moving a module to its own instance is a data migration plus a connection-string change, never a schema change.

Applying by hand (development):

```bash
createdb mysms
cd database
for f in $(ls migrations/*/V*.sql | awk -F/ '{print $NF"\t"$0}' | sort | cut -f2); do psql -v ON_ERROR_STOP=1 -d mysms -f "$f"; done
psql -v ON_ERROR_STOP=1 -d mysms -f verification/smoke.sql
```

## Verification performed

- The full DDL was applied to a clean **PostgreSQL 16.15** database with `ON_ERROR_STOP`. The catalog then held **460 tables** (635 relations including monthly partitions), **7,080 columns**, **469 foreign keys — 0 of them cross-schema**, **368 check constraints**, **232 unique constraints**, **251 partial/expression unique indexes** and **446 row-level-security policies**; all 446 tenant-owned tables have `FORCE` RLS (counted in the MySMS schemas only).
- Every column has a description (`COMMENT ON COLUMN`): 0 missing. Every foreign-key column is indexed, and so is every one of the 494 logical-reference columns (checked by the register generator, which refuses to write a register that disagrees with the catalog). The catalog holds no extensions, functions or triggers created by the schema.
- `verification/smoke.sql` passed: it seeds two tenants and proves that a cross-tenant guardian link is rejected by the tenant-composite FK; a duplicate gateway payment, a payerless payment, a target-less allocation, a duplicate fee due, a duplicate nested-term start, a second open placement in one year and a second open loan on one copy are all rejected; nested terms and same-year re-placement (history) are accepted; staff attendance routes into its monthly partition; and — connected as a non-owner role with `app.tenant_id` set — each tenant sees only its own rows (RLS isolation, both directions). Its third part asserts the distributed-deployment invariants: no foreign key crosses schemas; `idempotency_key` and `operation` exist in every service schema and `number_sequence` in exactly the seven number-issuing schemas; RLS isolates the module-local tables; a module issues a document number from its own sequence with `SELECT ... FOR UPDATE`. Its fourth part (SMOKE4) covers the hierarchical settings: one value per setting and scope, a tenant-level value names no scope id, a user-level value can never be locked, only catalogue settings can be set, and each tenant sees only its own values.
- ER diagrams are generated from the migrations alone; the generator asserts every table is drawn exactly once and every foreign key appears exactly once across the diagrams; the 494 cross-module logical references are noted on their rows from the same register as `logical-references.md`.
